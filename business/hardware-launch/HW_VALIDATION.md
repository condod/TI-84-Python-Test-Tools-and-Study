# Hardware Validation Record — the `.8xv` programs on real silicon

**This file is empty of results on purpose. Filling it in is the first real task of the launch.**

Created 2026-08-13 to hold the output of the blocking gate in
[`AB_TEST_PROTOCOL.md`](AB_TEST_PROTOCOL.md) §3.5.

---

## 0. Why this file exists

Every `.8xv` AppVar in `8xv/` was generated by this project's own converter (`tools/py_to_8xv.py`).
The conversion is **byte-exact against TI's reference output**, which proves the container format is
correct. **It has never been executed on a physical calculator.** The root `README.md` says so, and
[`../PREP_SOP.md`](../PREP_SOP.md) §5 says so.

Those are two different claims, and only the first one has evidence:

| Claim | Status |
|---|---|
| The `.8xv` container is byte-identical to what TI's software produces | **Verified**, by the converter's own test suite |
| The programs inside those containers launch, run and return correct answers on a TI-84 Plus CE Python | **Unverified.** This file is where that changes |

The desktop harness in `qa/` runs the `.py` sources under **CPython on a PC**. That catches logic
errors and it is why the known-answer values in §3.5.3 are trustworthy as *arithmetic*. It cannot
catch anything about **MicroPython on the CE**: missing modules, memory ceilings, `input()` behaviour
in the Python App shell, float formatting differences, or a program that simply will not start.

**A single unit and about an hour closes the most important open question in the repository.**

## 1. How to fill this in

Run the procedure in [`AB_TEST_PROTOCOL.md`](AB_TEST_PROTOCOL.md) §3.5 — that document is
authoritative for the known-answer inputs, the four pass criteria, and what to do on failure. Don't
re-derive them here.

Then record the result in §2 and §3 below, and write the summary fields into
[`AB_TEST_LOG.csv`](AB_TEST_LOG.csv) on the gate unit's row (`hw_gate_status`, `hw_gate_date`,
`payload_format`, `hw_gate_unit = TRUE`).

**Record failures in full.** A failure here is the most valuable single result this launch can
produce — it is worth more than the entire A/B test, because it is a fact about the product rather
than an estimate about the market. Do not summarise it as "didn't work."

```
  OS version AFTER flash  : _____   (expect 5.8.5 or later, PREP_SOP 4b)
  Bundle sent             : OS + Apps (.b84)?  [ ] yes   [ ] no
  Python App present      : [ ] yes  [ ] no    <-- if no, the OS-only bundle was sent
  TI Connect CE version   : _______
  Host OS                 : Windows 10
  Transfer destination    : [ ] RAM  [ ] Archive   <-- MUST be RAM (PREP_SOP 5)
  P6 total bytes measured : ______ B  (gate: <= 34,816 B)
  Outcome                 : [ ] PASS  [ ] FAIL_8XV_ONLY  [ ] FAIL_BOTH
                            [ ] PASS_AFTER_SUBSTITUTION
  payload_format adopted  : [ ] 8XV  [ ] PY
```

> **Two failure modes that are not program bugs — rule them out before blaming the code.**
>
> 1. **An All-Memory reset deletes the Python App itself.** A wiped unit boots, looks completely
>    normal, and has no Python at all until you send the **OS *and Apps*** bundle. If `PY` is missing
>    from the apps list, that is the cause, and it is not a converter fault.
> 2. **An AppVar sent to Archive does not appear in the Python App's File Manager.** TI: the Python
>    App only edits and runs AppVars **in RAM**. A program that "isn't there" may simply be archived.
>
> Neither of these is a gate failure. Fix and re-run.
