# File Format Research — TI-84 Plus CE Python AppVars (`.8xv`)

This is the working note for how these bundles ship **both** plain `.py` source and
ready-to-install `.8xv` Python AppVars, what the `.8xv` format actually is, the converter
we wrote, and — importantly — exactly how far the verification goes and where it stops.

**Short version:** the format is now fully documented below, we wrote a dependency-free
converter (`tools/py_to_8xv.py`), and it reproduces a Python AppVar generated by TI's own
software byte-for-byte. That is strong evidence, but it is not the same as watching a
program run on a real calculator, which we could not do here. See
[Verification status](#verification-status).

## What the on-calculator format is

- TI-84 Plus CE Python programs are **not** `.8xp` files. `.8xp` is the extension for
  compiled **TI-BASIC** programs on TI-83/84-series calculators.
- On-device, a Python program is stored as a **Python AppVar** with the extension
  **`.8xv`** (per Texas Instruments' TI Connect™ CE documentation and the TI-84 Plus CE
  Python eGuide).
- TI's normal workflow is: keep a plain `.py` text file on your computer and let TI Connect
  CE convert it to a `.8xv` Python AppVar when you send it to a connected calculator. Going
  the other way, TI Connect CE can pull a program back as either `.8xv` or `.py`.

## Is producing `.8xv` scriptable outside TI's GUI?

Officially, no. TI does not ship a documented command-line converter; `.py` → `.8xv` is a
TI Connect CE **GUI** feature. But the file format itself is a well-understood, long-since
reverse-engineered container, and it is entirely reasonable to write.

What we evaluated:

| Tool | Verdict |
|---|---|
| **`tivars_lib_py`** (PyPI `tivars`, v1.1.1, TI-Toolkit) | Actively maintained and correct for the **container**, but it has **no Python AppVar type**. Its `TIAppVar` is a generic AppVar (`_type_id = 0x15`) that treats the data section as opaque bytes; nothing in the library knows about the `PYCD` payload, and it does **not** enforce on-calculator name rules (it accepted `ok`, `1START`, and `A_B` in our probe, silently truncating over-long names). Useful as an independent cross-validator, not as a complete solution. |
| **`tivars_lib_cpp`** (adriweb) | Has a real `STH_PythonAppVar` type handler that documents the payload precisely, plus `testData/python_HELLO.8xv`, a genuine TI-generated fixture. This was our primary format reference. C++, so not directly usable, but invaluable as documentation. |
| **`tipyto8xv`** | Referenced in our earlier notes; we could not locate a current, maintained project under that name to evaluate. Not used. |

**What we did:** wrote our own converter, `tools/py_to_8xv.py`, using only the Python
standard library, and used `tivars_lib_py` as an *independent second implementation* to
cross-check the files we produce. Writing the container ourselves means the tool has no
third-party dependency and every byte is accounted for; cross-validating against a
separately-authored library means we're not just agreeing with ourselves.

## The format, byte by byte

Verified against `python_HELLO.8xv`, produced by **TI-SmartView CE 5.3.0.384**.

### Outer container (standard TI-8x variable file)

| Offset | Length | Contents |
|---|---|---|
| 0 | 8 | Signature `**TI83F*` |
| 8 | 2 | Export bytes `0x1A 0x0A` |
| 10 | 1 | Product ID. TI-SmartView wrote **`0x0A`**; this is a PC-side hint and is not used by the calculator. |
| 11 | 42 | Comment, ASCII, null-padded (TI wrote `Created by TI-Smartview CE 5.3.0.384`) |
| 53 | 2 | Length of the data section, little-endian |
| 55 | *n* | Data section (the variable entry, below) |
| 55+*n* | 2 | Checksum, little-endian |

Total file size is always `57 + n`.

### Variable entry (the data section)

| Offset | Length | Contents |
|---|---|---|
| 0 | 2 | Entry header length: **`0x000D`** (13) — the "flash" form that carries the version and archive bytes |
| 2 | 2 | Length of the variable data, little-endian |
| 4 | 1 | **Var type byte: `0x15`** (AppVar) |
| 5 | 8 | Variable name, ASCII, null-padded — this is the name shown in the Python App |
| 13 | 1 | Version (TI wrote `0x00`) |
| 14 | 1 | Archive flag: `0x80` archived, `0x00` in RAM. **TI wrote `0x00`.** |
| 15 | 2 | Length of the variable data again (must equal offset 2) |
| 17 | *m* | Variable data (the Python payload, below) |

### Python payload (the variable data)

| Offset | Length | Contents |
|---|---|---|
| 0 | 2 | Payload length, little-endian (i.e. *m* − 2) |
| 2 | 4 | **Magic `PYCD`** (plain source). `PYSC` is also accepted by the Python app. |
| 6 | … | Zero or more metadata records, then a `0x00` terminator |
| … | … | The raw script bytes |

Each metadata record is a length (7-bit continuation encoding, low group first, high bit set
to continue; the length counts the type byte), then a 1-byte type, then that many−1 data
bytes. Type `0x01` carries an original filename. **TI-SmartView wrote no metadata records at
all** — just the magic followed immediately by the `0x00` terminator — so our converter does
the same by default.

Script bytes are stored raw. TI's file uses **LF (`\n`) line endings and ends with a trailing
newline**, so the converter normalises CRLF and lone CR to LF, strips a UTF-8 BOM, and
appends a final newline if one is missing.

### Checksum

The trailing 2 bytes are the **low 16 bits of the sum of every byte in the data section**
(the variable entry — not the header, not the checksum itself), stored little-endian:

```python
checksum = sum(entry_bytes) & 0xFFFF
```

Confirmed against TI's file: stored `0x0E72`, computed `0x0E72`.

### On-calculator name rules

The name field is 8 bytes, null-padded. Legal names are **1–8 characters, `A`–`Z` and
`0`–`9`, starting with a letter** (TI's own docs show names like `SCRIPT1`, `VABSOLUE`).
`tivars_lib_py` does not enforce this, so `py_to_8xv.py` validates it itself and refuses
anything illegal rather than writing a file the calculator would reject.

Because 8 characters is tight, `tools/varnames.json` maps each program to a hand-picked
name (`quadratic_solver.py` → `QUADSOLV`, `stoichiometry_molar_mass.py` → `MOLARMAS`) so the
Python App's program list stays readable. Anything not listed falls back to automatic
derivation with collision-avoidance.

## The converter

`tools/py_to_8xv.py` — Python 3.8+, **standard library only**, no dependencies.

```bash
# one file
python tools/py_to_8xv.py calculus/simpsons_rule.py -o SIMPSON.8xv --name SIMPSON

# the whole library, mirroring subject folders, using the curated names
python tools/py_to_8xv.py --batch . --out ./8xv --names tools/varnames.json \
    --name-by-var --comment "TI-84 CE Python Study Toolkit"
```

`--name-by-var` names each output after the on-calculator variable name (so
`QUADSOLV.8xv` installs as `QUADSOLV`); without it, outputs keep the source file's stem.
Batch mode skips `tools/`, `8xv/`, `bundles/`, caches and dotted folders by default;
`--skip DIR` excludes more, and `--only DIR` restricts the walk to named subfolders if you
ever need a build to ignore unrelated `.py` files elsewhere in the tree.

Every conversion parses its own output back and re-checks it before the file is written, so
a corrupt file fails loudly instead of shipping.

Supporting tools:

- `tools/verify_8xv.py` — the verification harness described below.
- `tools/test_py_to_8xv.py` — 48 unit-style checks (round-trip, name rules, corruption detection).
- `tools/build_bundles.py` — rebuilds the ZIP bundles in `bundles/` from `bundles/readme/*.md`
  plus the `.py` and `.8xv` trees.

### Rebuilding everything

```bash
python tools/py_to_8xv.py --batch . --out ./8xv --names tools/varnames.json --name-by-var \
    --comment "TI-84 CE Python Study Toolkit"
python tools/build_bundles.py --repo .
python tools/verify_8xv.py --src . --out ./8xv --names tools/varnames.json --name-by-var \
    --bundles ./bundles
python tools/test_py_to_8xv.py path/to/python_HELLO.8xv   # optional; see below
```

Adding a program? Give it a name in `tools/varnames.json`, then re-run the above.
`build_bundles.py` prints a note listing any program that isn't in a bundle yet.

**If you edit a `.py` file, re-run all three.** The `.8xv` files are build outputs; nothing
detects a stale one automatically except the verifier.

## Verification status

### What is proven

- **Byte-exact reproduction of TI's own output.** Given the same script, name, comment,
  version and product ID, our converter reproduces `python_HELLO.8xv` — a file written by
  TI-SmartView CE 5.3.0.384 — byte for byte, all 111 of them. Our understanding of the
  layout is therefore not merely self-consistent; it agrees exactly with TI's software on a
  real example.
- **Structural validity, 29/29 programs.** Signature, export bytes, header length, var type
  byte `0x15`, both variable-data length fields agreeing with each other and with the actual
  data, the payload length prefix, the `PYCD` magic, the metadata terminator, and the
  recomputed checksum.
- **Clean round-trip, 29/29 programs.** Parsing each generated `.8xv` recovers the script
  byte-for-byte identical to the normalised source.
- **Independent cross-validation, 29/29 programs.** `tivars_lib_py` — a separately-authored
  implementation — opens every file we generate, reads back the expected name and type ID
  `0x15`, and re-serialises to bytes identical to ours.
- **The checks are not vacuous.** `tools/test_py_to_8xv.py` flips one byte at a time across
  13 structurally distinct positions (signature, both length fields, type byte, name, payload
  prefix, magic, terminator, script body, checksum) and also tries truncated, over-long,
  empty, and non-var input. All 17 corruptions are rejected. 48/48 checks pass.
- **The shipped artifacts, not just the intermediates.** The verifier opens each ZIP bundle
  and confirms every `.8xv` inside matches a `.py` in the same bundle by recovered script,
  that the README documents each on-calculator name, and that the exam-policy disclaimer is
  present. 51 AppVars checked across the 6 bundles.

### What is NOT proven

- **Nothing was run on a calculator.** No TI-84 Plus CE Python hardware and no emulator was
  available in this environment. We have not observed any of these files being sent by TI
  Connect CE, appearing in the Python App, opening in the editor, or executing.
- **TI Connect CE has not opened these files.** Our evidence that TI's tooling accepts this
  layout is that we reproduce TI's own output exactly — which is strong, but is inference,
  not observation.
- **The programs' own runtime behaviour is unchanged but also unverified here.** Conversion
  is lossless (proven by round-trip), so an `.8xv` runs exactly what the `.py` contains — but
  whether each program behaves correctly on-device is a separate question this work doesn't
  address.
- **Edge cases we can't see.** Anything about how the Python App handles a name collision
  with an existing on-calculator program, or behaviour at the ~50 KB storage ceiling, is
  untested. The largest AppVar here is 5,391 bytes and all 29 together come to 106,409 bytes
  (103.9 KB), which is **over** the ~50 KB on-device guideline if installed all at once —
  buyers should install the subjects they need rather than everything.

### Recommended owner check (about 5 minutes, needs a calculator)

Do this once before promoting the `.8xv` files heavily in the store listing:

1. Install TI Connect™ CE and connect a TI-84 Plus CE **Python Edition** over USB.
2. Drag `8xv/algebra_linear_stats/QUADSOLV.8xv` onto Calculator Explorer. Confirm it appears
   as `QUADSOLV`, listed as **AppVar Python** (TI Connect CE labels Python AppVars this way).
3. On the calculator, open the **Python App**, confirm `QUADSOLV` is in the program list,
   open it in the editor to confirm the source is intact, and **Run** it.
4. Repeat with one large program (`chemistry_and_exam_tools/IDEALGAS.8xv`, ~4.8 KB) to check
   there's no size-related problem.
5. For a belt-and-braces comparison, send `algebra_linear_stats/quadratic_solver.py` through
   TI Connect CE, pull the resulting AppVar back to the computer as `.8xv`, and diff it
   against ours. Expect the 42-byte comment field to differ (TI writes its own) and possibly
   the product-ID byte; everything else should match.

If step 3 works, the pipeline is confirmed end-to-end and this section can be updated to say
so. If it doesn't, the `.py` files in every bundle remain a complete, working product — the
install instructions cover both paths precisely so that no buyer is ever blocked.

## What ships in the bundles

Every bundle contains each program twice: `8xv/` with the ready-to-install Python AppVars and
`py/` with the plain-text source. Each bundle README explains both install paths (drag the
`.8xv` onto TI Connect CE, or drag the `.py` and let TI Connect CE convert it), states plainly
that the `.8xv` files came from our own converter rather than TI's, and points at the `.py`
route as the fallback. The exam-policy disclaimer is unchanged and present in all six.

**Bundle membership is unchanged** — the same 24 programs as before. Five newer programs
(`complex_number_calculator`, `heat_transfer_calculator`, `oblique_triangle_solver`,
`punnett_square_solver`, `discrete_math_toolkit`) have `.8xv` files in `8xv/` but are not in
any bundle yet, because which programs go in which paid product — and what that does to
pricing — is a call for the owner rather than the build script. To add them, extend the
program lists at the top of `tools/build_bundles.py`, mention them in the matching
`bundles/readme/*.md`, and re-run the build. `build_bundles.py` prints a reminder listing
every unbundled program each time it runs.
